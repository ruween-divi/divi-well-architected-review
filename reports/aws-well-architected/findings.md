**Description**
FreeStorageSpace was 0 GB on 14, 15, 16 and 17 August 2026: the instance was storage-full, the state in which RDS shuts the database down.
It was then grown to 1,250 GiB, but MaxAllocatedStorage is also 1,250 GiB, so storage autoscaling cannot add space. Free space fell from 427.7 GB
(30 Oct minimum) to 394.3 GB (11 Nov minimum), roughly 2.8 GB/day [Estimated], which leaves about 140–150 days at today's rate [Estimated];
a bulk load (for example a CDC backfill for a new tenant) would shorten that sharply. No alarm watches free storage (AWS-WA-008).

**Evidence**
- FreeStorageSpace daily minimum 0.0 GB on 2026-08-14/15/16/17; 311.6 GB on 2026-08-18; 415.2 GB at 2026-11-12 06:50 UTC [Measured · AWS/RDS · 1-day period]
- AllocatedStorage 1250, MaxAllocatedStorage 1250, gp3 12,000 IOPS / 500 MiB/s, status available, no pending changes [Confirmed · rds describe-db-instances]
- Daily minimum free space 427.7 GB (2026-10-30) → 394.3 GB (2026-11-11) [Measured]

**Business impact**
A storage-full event stops writes for every tenant and API stack that uses the database; the August event lasted days.

**Technical impact**
Database shutdown at the storage-full threshold. Autoscaling cannot act because the threshold equals the current size, and storage changes are
limited (storage optimisation, four modifications per 24 h), so recovery can take hours.

**Recommended remediation**
1. Raise MaxAllocatedStorage now (for example 1,600–2,000 GiB; AWS recommends at least 26% above allocated). No cost until storage is used.
2. Alarm on FreeStorageSpace (for example below 20% and below 10% of allocated) and subscribe to RDS events RDS-EVENT-0089, -0221 and -0224 (AWS-WA-008).
3. Find what is growing: table and index sizes, dead tuples (Performance Insights, `pg_stat_user_tables`), CDC landing-table retention; establish the cause of the August event.
4. Verify: MaxAllocatedStorage above AllocatedStorage, alarm in OK state, growth rate documented.
*Do not / alternatives considered:* do not pre-allocate a large fixed increase before the growth analysis; allocated storage cannot be reduced later.

**Implementation complexity:** Low (setting change in Terraform, no downtime for the threshold)
**Trade-offs / risks:** autoscaled storage cannot shrink; cost grows with data ($0.138/GB-month single-AZ, $0.276 Multi-AZ, Sydney list).

**Cost impact**
None until storage grows; each additional 100 GB allocated ≈ $13.80/month single-AZ [Estimated · AWS Pricing API 2026-11-12].

**References**
- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIOPS.Autoscaling.html — threshold must exceed allocated storage; storage-full behaviour
- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_Events.Messages.html — RDS-EVENT-0221 (storage-full, shut down), RDS-EVENT-0224

**Description**
Both connectors' configurations contain `database.user` and `database.password`, and neither has a custom worker configuration. MSK Connect resolves
Secrets Manager or Parameter Store references only through config providers declared in a worker configuration, so both passwords are stored literally
and returned by `DescribeConnector`. The nocelle connector reads the tenant's **production** ERP database from the staging account, so a production
credential of a customer sits in plain text in staging. Both also use `database.trustServerCertificate=true` and `errors.log.include.messages=true`
(record contents of failed records in the connector logs).

**Evidence**
- `kafkaconnect list-connectors` / `describe-connector`: workerConfiguration null on both; `database.password` present in both configurations [Confirmed · keys only]
- debezium-connector: `database.names=GcorpNocelle` (same database as production); debezium-dug: `dug_uat` [Confirmed]
- AWS documentation: config providers are defined in worker configurations and keep secrets out of plain text [Confirmed · MSK developer guide]

**Business impact**
A leaked tenant credential is a breach of the customer's own ERP system; staging usually has wider access than production.

**Technical impact**
Credentials readable through the console and API by every read-only user of the staging account; record contents may sit in logs.

**Recommended remediation**
1. Move both credentials to Secrets Manager behind a config provider (custom worker configuration); recreate or update the connectors.
2. Ask nocelle to rotate the `GcorpNocelle` login(s) used by staging and production, and give staging its own least-privilege login, or a non-production copy (AWS-WA-014).
3. Set `errors.log.include.messages=false`; review log retention for record contents.
4. If a connector is retired (AWS-WA-024, AWS-WA-025), rotate its password and delete it.
*Do not / alternatives considered:* do not paste current values into tickets or chat when checking.

**Implementation complexity:** Medium
**Trade-offs / risks:** connector recreation must be coordinated with the re-snapshot plans.

**Cost impact**
$0.40 per secret per month [Estimated].
